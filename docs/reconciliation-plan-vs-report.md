# مفاضلة: تقرير المقارنة مقابل خطة الأولويات

تاريخ المفاضلة: 2026-07-09
الأساس: `docs/project-comparison-report.md` + `docs/priority-plan.md` + فحص كود المشروع الفعلي.

## 1. الغرض

هذه الوثيقة تفاضل بين التقرير (تقييم الوضع الحالي مقابل متطلبات v6/v7 وعدم وجود SSL) والخطة (14 أولوية موزعة على 5 مراحل)، لتنتج **قائمة أولويات موحّدة واحدة** خالية من التكرار، مع تحديد الفجوات وترتيب التنفيذ.

## 2. ملخص الوثيقتين

- **التقرير** (`project-comparison-report.md`): وثيقة تقييم. تقرّ بأن المشروع منظومة تشغيلية حقيقية متوافقة مع توثيق `AGENTS.md`، وتحدّد قيدين حاكمين: دعم RouterOS v6/v7، وعدم افتراض شهادة SSL (لذا المنفذ `8728` عبر `librouteros` هو المسار الافتراضي الصحيح). ترفع مخاطر الاتصال غير المشفر وتوصي بتخفيفها شبكياً، وتسرد مميزات مدير الشبكة حسب الأولوية.
- **الخطة** (`priority-plan.md`): وثيقة تنفيذ. تفصّل 14 أولوية في 5 مراحل (استقرار/أمان تشغيل، توافق v6/v7، مميزات مدير عالية القيمة، توسع منظم، تنظيف معماري تدريجي) مع معايير قبول وملاحظات توافق.

## 3. نقاط الاتفاق (الثوابت المعمارية)

الوثيقتان متفقتان تماماً على الآتي، وهي خط أحمر لا يُحرّك أثناء التنفيذ:

1. `DEFAULT_API_PORT = 8728` يبقى كما هو؛ لا يُفرض API-SSL ولا REST/HTTPS كمسار أساسي.
2. `librouteros` يبقى طبقة الاتصال الموحدة للإصدارين v6/v7.
3. `get_userman_base_path()` يبقى المرجع المركزي لاختيار المسار (v7=`user-manager`، v6=`tool/user-manager`، والافتراض عند جهل الإصدار = v6 المحافظ).
4. التسجيل المركزي في `utils/registrations.py`، وعدم إضافة handlers في `main.py`.
5. أي عملية متزامنة/بطيئة تمر عبر `run_blocking()`؛ العمليات الثقيلة (backup/restore/قوائم كبيرة) عبر `execute_long()`.
6. `core/` تبقى خالية من اعتماد Telegram (تُعيد DTO/بيانات خام قابلة للاختبار).
7. بوابات الجودة: `ruff check . --select F821` + `scripts/validate_handlers.py` + `py_compile` + `pytest` (تُشغَّل عبر `py -3.12`).
8. كلمات المرور مشفّرة (Fernet)، ولا تُعرض في الرسائل أو السجلات.

## 4. المفاضلة: التباينات والفجوات

### 4.1 ما ورد في التقرير كأولوية عالية وليس في الخطة كأولوية مستقلة

| بند من التقرير | أولوية التقرير | وضعه في الخطة |
|---|---|---|
| **التنبيهات الذكية** (انقطاع/عودة الراوتر، فشل backup، تكرار فشل API، فشل restore/reboot) | عالية #2 | **غائب كأولوية مستقلة**. الخطة تلمسه جزئياً فقط (إشعار فشل backup موجود في `core/backup_scheduler.py`، وwatchdog يكتشف offline) لكن لا توجد استراتيجية تنبيه موحّدة. |
| **شاشة "System status" الخاصة بالبوت** (حالة venv/Python، عدد الراوترات، آخر backup، آخر فشل watchdog، حجم DB) | ضمن أفضل الممارسات التشغيلية | الخطة (أولوية 6) تغطي حالة الراوترات فقط، لا حالة البوت نفسه. |

> **قرار مقترح**: رفع "التنبيهات الذكية" إلى أولوية مستقلة (انظر القائمة الموحّدة أدناه) لأن التقرير يصنّفها عالية وتؤثر على موثوقية التشغيل.

### 4.2 ما ورد في الخطة ولم يُبرزه التقرير صراحةً

- **أولوية 2 (بيئة Python والـ Quality Gates)**: التقرير يذكرها كملاحظة بيئة (الـ venv معطوب يشير إلى Python غير موجود، يُستخدم `py -3.12`)، والخطة تحوّلها إلى أولوية تنفيذية مع `requirements-dev.txt`. **تم التحقق**: `requirements-dev.txt` موجود فعلاً، و`tests/core/` فيها 10 ملفات اختبار. لذا هذه الأولوية مؤسَّسة وسليمة.
- **أولوية 3 (عزل ملفات التشغيل المحلية)**: التقرير يذكرها كخطر تشغيلي؛ الخطة ترفعها لأولوية. متفق.
- **أولوية 11 (دفعات الكروت / batches)**: لم ترد في التقرير إلا ضمنياً (تحسين إدارة الكروت/أرشفة لاحقة). الخطة تسبق التقرير هنا.
- **أولويات 12–14 (تنظيف معماري تدريجي)**: الخطة أكثر تحديداً من التقرير الذي اكتفى بإشارات عامة.

### 4.3 اختلاف ترتيب التنفيذ

- التقرير (القسم 6): dashboard ← **alerts** ← audit filter ← backup ← reports ← roles ← card mgmt.
- الخطة ("ترتيب التنفيذ المقترح"): 8728 docs ← python env ← compat matrix ← status dashboard ← backup history ← logs filters ← roles ← hotspot reports ← card batches ← cleanup.
- **التباين الجوهري**: الخطة أعطت أولوية للتوثيق/الاستقرار (8728، python، compat) قبل المميزات، وهو صحيح؛ لكنها **أسقطت التنبيهات** التي يضعها التقرير في المركز الثاني مباشرة بعد اللوحة.

### 4.4 مخاطر وتناقضات صغرى

- **فترة كاش الإصدار**: `get_version()` يخزّن الإصدار طويلاً (connection_pool `router_versions` TTL 24 ساعة). بعد ترقية RouterOS قد يبقى المسار القديم مستخدماً. الوثيقتان لا تعالجان إبطال الكاش عند ترقية الراوتر →建议 إضافة `invalidate` صريح عند نجاح الاتصال/إعادة التسمية. (لم تُدرج بعد كأولوية.)
- **v6/v7 restore fields**: الخطة أولوية 5 تتطلب دفاعية عند رفض حقل؛ التقرير يحذّر من نفس الخطر. متفق لكن يلزم ربطه باختبارات `tests/core/` موجودة فعلاً (verify عملي على راوتر حقيقي لا يغطّيه mock).

## 6. ترتيب التنفيذ المقترح

1. أولويات 1–3 (استقرار/أمان وتوثيق) — بلا تغيير سلوكي جوهري، منخفضة المخاطر.
2. أولويات 4–6 (توافق v6/v7) — تثبيت صحة الاتصال قبل بناء المميزات.
3. أولويات 7–10 (لوحة الحالة + التنبيهات + النسخ + السجل) — قيمة تشغيلية عالية لمدير الشبكة.
4. أولويات 11–13 (أدوار + تقارير + دفعات) — توسع منظم.
5. أولوية 14 (تنظيف) — يُنفَّذ تدريجياً أثناء كل مرحلة لا كدفعة واحدة.

## 7. بوابات الجودة لكل أولوية

```
ruff check . --select F821 --exclude venv --exclude __pycache__ --exclude backups --exclude logs --exclude _releases
py -3.12 scripts/validate_handlers.py
py -3.12 -m pytest -q
```
عند المسّ بـ handlers/commands: تحديث `utils/registrations.py` + `utils/bot_commands.py` + `bot/messages.py` + تشغيل `validate_handlers.py`.

## 8. قرارات مفتوحة / أسئلة للتأكيد

1. هل نُبقي "التنبيهات الذكية" (الأولوية 8 هنا) ضمن نطاق التنفيذ القريب، أم نؤجلها لمرحلة لاحقة رغم تصنيف التقرير لها "عالية"؟ **توصيتي: إدراجها الآن** لأنها تعتمد على بنية watchdog/backup الموجودة.
2. مستوى تنفيذ الأولوية 1: توثيق فقط (README/AGENTS/docs) أم إضافة فحص startup يحذّر إن كان `BACKUP_DIR`/`mikrotik_bot.db`/`logs/` داخل مجلد قابل للمزامنة؟ **توصيتي: توثيق + تحذير startup خفيف غير مانع.**
3. نطاق الأدوار (11): هل نخزّن الأدوار في `database/models.py` (جدول جديد) أم في `.env`/config؟ **توصيتي: جدول DB جديد مع fallback إلى ADMIN_IDS الحالي** لتفادي كسر القائمة القديمة.
4. هل تُنقل التنبيهات واللوحة إلى اختبارات `tests/integration/` حقيقية على راوتر، أم نكتفي بـ mocks الموجودة؟ (الـ mock لا يغطّي فارق حقول v6/v7 الفعلي.)
