# خطة أولويات تطوير مشروع MikroTik Telegram Bot

تاريخ الخطة: 2026-07-09

## الملخص

هذه الخطة ترتب أولويات التطوير بناءً على واقع الكود الحالي، تقرير المقارنة في `docs/project-comparison-report.md`، وتقييم هيكلة الملفات وتصميم البوت.

المعايير الحاكمة:

- دعم RouterOS v6 وRouterOS v7.
- عدم فرض SSL أو REST لأن الراوترات لا تملك شهادة SSL.
- اعتماد RouterOS API العادي على المنفذ `8728` كمسار افتراضي، مع ضوابط أمان شبكية واضحة.
- تنفيذ التحسينات تدريجياً بدون إعادة هيكلة واسعة تكسر الاختبارات أو تدفقات Telegram الحالية.

## المرحلة 1: استقرار وأمان التشغيل

### أولوية 1: تشديد تشغيل API على المنفذ 8728

الهدف: جعل استخدام API غير المشفر خياراً مضبوطاً لا مخاطرة مفتوحة.

المناطق المتوقعة:

- `README.md`
- `AGENTS.md`
- وثائق التشغيل داخل `docs/`

سبب الأولوية:

الاتصال الحالي عبر `librouteros` و`8728` مناسب لدعم v6/v7، لكنه غير مشفر. الخطر الأساسي ليس في الكود بل في تشغيل المنفذ داخل شبكة غير مقيدة أو تعريضه للإنترنت.

معيار القبول:

- التوثيق يوضح أن `8728` مقبول فقط داخل شبكة موثوقة ومقيدة.
- إضافة توصيات صريحة مثل تقييد خدمة API على IP جهاز البوت، منع الوصول من WAN، واستخدام مستخدم MikroTik محدود الصلاحيات.
- عدم اقتراح REST/HTTPS كمسار أساسي.

ملاحظات التوافق:

- لا يتم تغيير `DEFAULT_API_PORT = 8728`.
- لا يتم فرض API-SSL أو شهادة.

### أولوية 2: إصلاح أو توثيق بيئة Python

الهدف: جعل Quality Gates قابلة للتشغيل من مسار واضح ومتكرر.

المناطق المتوقعة:

- `README.md`
- `requirements.txt`
- `requirements-dev.txt`
- بيئة التشغيل المحلية خارج الكود عند الحاجة

سبب الأولوية:

الفحص السابق أظهر أن `venv\Scripts\python.exe` يشير إلى Python غير موجود، بينما نجح التشغيل باستخدام `py -3.12`.

معيار القبول:

- وجود طريقة موثقة واحدة لتشغيل الفحوص.
- نجاح الأوامر:
  - `ruff check . --select F821`
  - `py -3.12 scripts\validate_handlers.py`
  - `py -3.12 -m pytest -q`

ملاحظات التوافق:

- لا علاقة مباشرة بإصدارات RouterOS.
- الهدف تقليل أعطال التطوير والنشر.

### أولوية 3: عزل ملفات التشغيل المحلية

الهدف: تقليل مخاطر تسريب قاعدة البيانات والنسخ والسجلات.

المناطق المتوقعة:

- `.gitignore`
- `README.md`
- إعدادات التشغيل المحلية

سبب الأولوية:

ملفات مثل `mikrotik_bot.db`, `backups/`, `logs/`, و`venv/` موجودة على القرص. `.gitignore` يحتوي قواعد مناسبة، لكن يجب إبقاء هذا الخطر واضحاً في التشغيل والنسخ.

معيار القبول:

- توثيق واضح بعدم مشاركة ملفات التشغيل.
- بقاء `.env`, `*.db`, `backups/`, `logs/`, و`venv/` خارج Git.

ملاحظات التوافق:

- لا يغير سلوك البوت.

## المرحلة 2: توافق RouterOS v6/v7

### أولوية 4: مصفوفة توافق أوامر RouterOS

الهدف: توثيق الأوامر والحقول الحساسة التي تختلف أو قد تختلف بين v6 وv7.

المناطق المتوقعة:

- `docs/routeros-compatibility.md`
- `core/mikrotik_api.py`
- اختبارات `tests/core/`

سبب الأولوية:

User Manager هو أكثر جزء معرض للاختلاف، خصوصاً المسارات والحقول في profiles/users وrestore.

معيار القبول:

- توثيق المسارات:
  - v6: `tool/user-manager`
  - v7: `user-manager`
- توثيق أوامر Hotspot وbackup/restore وreset counters.
- وجود اختبارات تؤكد اختيار المسار الصحيح لكل إصدار.

ملاحظات التوافق:

- الحفاظ على `get_userman_base_path()` كمرجع مركزي.
- عند فشل معرفة الإصدار، يبقى الافتراض المحافظ هو v6.

### أولوية 5: تقوية استعادة User Manager

الهدف: تقليل فشل restore بسبب حقول غير مدعومة بين v6 وv7.

المناطق المتوقعة:

- `core/backup/userman.py`
- `tests/core/`
- `tests/integration/`

سبب الأولوية:

الاستعادة الحالية عملية، لكنها تضيف حقولاً قد تختلف حسب الإصدار. يجب جعلها أكثر دفاعية عند رفض RouterOS لبعض الحقول.

معيار القبول:

- عند رفض حقل في profile أو user، يتم تسجيل خطأ واضح واستكمال بقية العناصر إن أمكن.
- وجود اختبارات لحالات partial restore.

ملاحظات التوافق:

- لا يتم الاعتماد على REST.
- لا يتم فرض SSL.

## المرحلة 3: مميزات مدير الشبكة عالية القيمة

### أولوية 6: لوحة حالة الراوترات

الهدف: إعطاء مدير الشبكة ملخصاً سريعاً عن كل الراوترات.

المناطق المتوقعة:

- `bot/handlers/watchdog.py`
- `core/watchdog.py`
- `core/stats.py`
- `bot/keyboards.py`
- `bot/messages.py`
- `utils/registrations.py`

سبب الأولوية:

مدير الشبكة يحتاج معرفة الحالة قبل تنفيذ أي عملية: هل الراوتر متصل؟ ما الإصدار؟ كم مستخدماً نشطاً؟ متى آخر backup؟

معيار القبول:

- أمر أو زر واحد يعرض لكل راوتر:
  - online/offline
  - آخر فحص
  - RouterOS version
  - عدد Hotspot active إن أمكن
  - آخر backup ناجح أو فاشل عند توفره

ملاحظات التوافق:

- استخدام أوامر RouterOS API المتوافقة مع v6/v7.
- أي عملية بطيئة تمر عبر `run_blocking()`.

### أولوية 7: تحسين النسخ الاحتياطي

الهدف: جعل backup قابلاً للمراجعة والاعتماد لا مجرد عملية لحظية.

المناطق المتوقعة:

- `core/backup_scheduler.py`
- `core/backup_service.py`
- `database/models.py` أو وحدة database جديدة
- `bot/handlers/backup.py`

سبب الأولوية:

النسخ الاحتياطي من أعلى العمليات قيمة وخطورة. يلزم معرفة آخر نجاح/فشل لكل راوتر وسياسة الاحتفاظ.

معيار القبول:

- تخزين نتيجة كل backup مجدول.
- عرض آخر نتيجة backup من داخل البوت.
- retention قابل للضبط أو موثق بوضوح.
- تنبيه عند فشل backup.

ملاحظات التوافق:

- لا تغيير في آلية الاتصال الأساسية.
- الحفاظ على `execute_long()` للعمليات الثقيلة.

### أولوية 8: سجل تدقيق قابل للتصفية

الهدف: جعل `/logs` مفيداً في التشغيل اليومي والتحقيق.

المناطق المتوقعة:

- `database/models.py` أو وحدة logs منفصلة
- `bot/handlers/audit.py`
- `bot/keyboards.py`
- `utils/registrations.py`

سبب الأولوية:

السجل موجود، لكنه يحتاج فلاتر عملية عند زيادة عدد العمليات والمشرفين والراوترات.

معيار القبول:

- التصفية حسب:
  - الراوتر
  - المشرف
  - العملية
  - التاريخ أو آخر مدة
- بقاء pagination واضحاً وسهل الاستخدام.

ملاحظات التوافق:

- لا علاقة مباشرة بإصدارات RouterOS.
- يجب عدم تسجيل كلمات مرور أو أسرار.

## المرحلة 4: توسع منظم

### أولوية 9: أدوار داخل البوت

الهدف: تقليل مخاطر إعطاء كل المشرفين صلاحيات كاملة.

المناطق المتوقعة:

- `config.py`
- `utils/admin_decorator.py`
- `database/models.py`
- handlers الحساسة مثل reboot, restore, delete router, backup

سبب الأولوية:

`ADMIN_IDS` مناسب كبداية، لكنه لا يفرق بين مالك النظام وموظف إصدار الكروت أو شخص يقرأ التقارير فقط.

معيار القبول:

- دعم أدوار:
  - Owner/Admin
  - Operator
  - Viewer
- Operator لا يستطيع تنفيذ reboot أو restore أو حذف راوتر.
- Viewer لا يستطيع تعديل بيانات أو إنشاء كروت.

ملاحظات التوافق:

- لا يؤثر على RouterOS v6/v7.
- يجب أن تكون الأخطاء واضحة للمستخدم وغير كاشفة للتفاصيل.

### أولوية 10: تقارير Hotspot قابلة للتصدير

الهدف: تحويل بيانات الاستخدام إلى قيمة إدارية قابلة للمشاركة.

المناطق المتوقعة:

- `core/hotspot_manager.py`
- `core/stats.py`
- `bot/handlers/usage.py`
- `pdf/` عند الحاجة

سبب الأولوية:

مدير الشبكة يحتاج تقارير أكثر من عرض مستخدم واحد: الأكثر استهلاكاً، المنتهية، غير النشطة، والمقتربة من الحد.

معيار القبول:

- تقرير داخل Telegram.
- تصدير CSV أو PDF للبيانات الأساسية.
- معالجة القوائم الكبيرة باستخدام `execute_long()` أو pagination.

ملاحظات التوافق:

- الاعتماد على أوامر Hotspot المتوافقة مع v6/v7.

### أولوية 11: إدارة batches للكروت

الهدف: تحسين دورة إصدار وبيع وإعادة طباعة الكروت.

المناطق المتوقعة:

- `core/hotspot_manager.py`
- `core/userman_manager.py`
- `database/models.py`
- `bot/handlers/hotspot_cards.py`
- `bot/handlers/userman.py`

سبب الأولوية:

إنشاء الكروت موجود، لكن مدير الشبكة يحتاج تتبع الدفعات، إعادة الطباعة، وربط الكروت بسياق تجاري أو تشغيلي.

معيار القبول:

- حفظ batch باسم وتاريخ ونوع.
- عرض batches السابقة.
- إعادة توليد PDF لدفعة محفوظة.

ملاحظات التوافق:

- يجب عدم حفظ كلمات مرور غير مشفرة إذا أضيف تخزين دائم للكروت.

## المرحلة 5: تنظيف معماري تدريجي

### أولوية 12: تقسيم قاعدة البيانات عند الحاجة

الهدف: تخفيف تضخم `database/models.py` بدون refactor شامل مبكر.

المناطق المتوقعة:

- `database/routers.py`
- `database/sessions.py`
- `database/logs.py`
- `database/settings.py`
- `database/backup_jobs.py`

سبب الأولوية:

`models.py` يجمع schema وCRUD وmigrations خفيفة. هذا مقبول الآن، لكنه سيزداد تعقيداً مع roles وbackup history وتقارير batches.

معيار القبول:

- عند إضافة ميزة database جديدة، توضع في وحدة مناسبة بدلاً من زيادة `models.py` إن كان ذلك عملياً.
- الحفاظ على واجهات توافق عند الحاجة حتى لا تنكسر imports القديمة.

ملاحظات التوافق:

- أي migration يجب أن يكون idempotent.
- يجب تشغيل اختبارات database بعد كل تعديل.

### أولوية 13: تقسيم الرسائل ولوحات المفاتيح حسب المجال

الهدف: تحسين قابلية صيانة `bot/messages.py` و`bot/keyboards.py`.

المناطق المتوقعة:

- `bot/messages/`
- `bot/keyboards/`
- أو تقسيم تدريجي بملفات مثل `bot/messages_backup.py` إذا كان أقل كلفة

سبب الأولوية:

الملفان كبيران، وأي ميزة جديدة ستزيد التضخم. التقسيم حسب المجال يقلل التعارضات ويجعل التعديل أسهل.

معيار القبول:

- لا يتم التقسيم دفعة واحدة.
- عند تعديل مجال كبير مثل backup أو reports، يمكن نقل رسائله/لوحاته إلى ملف خاص مع إبقاء imports واضحة.

ملاحظات التوافق:

- أي تغيير في commands أو رسائل المستخدم يجب أن ينعكس في `utils/bot_commands.py` و`bot/messages.py` أو البديل الجديد.

### أولوية 14: الحفاظ على استقلال `core/`

الهدف: منع تسرب Telegram إلى منطق الأعمال.

المناطق المتوقعة:

- `core/metrics.py`
- خدمات `core/`
- handlers المقابلة

سبب الأولوية:

طبقة `core/` يجب أن تبقى قابلة للاختبار بدون Telegram. وجود imports من Telegram داخل `core` يجب عزله تدريجياً إذا كان متعلقاً بعرض أمر أو handler.

معيار القبول:

- المنطق الذي يحتاج `Update` أو `ContextTypes` يبقى في `bot/handlers` أو `utils`.
- `core` يعيد بيانات خام أو DTO بسيطة قابلة للاختبار.

ملاحظات التوافق:

- لا تغيير سلوكي مطلوب.
- refactor تدريجي عند لمس الملف.

## بوابات الجودة لكل مرحلة

قبل اعتماد أي تنفيذ:

```bash
ruff check . --select F821
py -3.12 scripts\validate_handlers.py
py -3.12 -m pytest -q
```

عند تعديل handlers أو commands:

- تحديث `utils/registrations.py`.
- تحديث `utils/bot_commands.py`.
- تحديث رسائل المستخدم في `bot/messages.py` أو ملف الرسائل البديل.
- تشغيل `scripts\validate_handlers.py`.

## ترتيب التنفيذ المقترح

1. تشديد توثيق تشغيل `8728` بدون SSL.
2. إصلاح أو توثيق بيئة Python وQuality Gates.
3. إنشاء مصفوفة توافق RouterOS v6/v7.
4. إضافة لوحة حالة الراوترات.
5. تحسين backup history وretention والتنبيهات.
6. تطوير فلاتر `/logs`.
7. إضافة أدوار داخل البوت.
8. إضافة تقارير Hotspot قابلة للتصدير.
9. إضافة batches للكروت.
10. تنفيذ التنظيف المعماري تدريجياً أثناء العمل على الميزات السابقة.
