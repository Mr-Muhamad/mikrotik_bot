# خطة تكميلية: ما بعد خطة الأولويات (أفضل الممارسات الهندسية)

تاريخ الخطة: 2026-07-09
الأساس: `docs/project-comparison-report.md` + `docs/priority-plan.md` + `docs/reconciliation-plan-vs-report.md`
الغرض: تغطية الفجوات الهندسية التي لم تعالجها الخطة الأصلية (14 أولوية). هذه الخطة **مكملة لا بديلة**، وتُنفَّذ بالتوازي أو بعد المرحلة 5 من الخطة الموحّدة، دون كسر الثوابت المعمارية.

## العلاقة بالخطة الأصلية

الخطة الأصلية غطّت: الاستقرار/الأمان التشغيلي، توافق v6/v7، مميزات مدير الشبكة، التوسع، والتنظيف المعماري. هذه الخطة تغطي: **الأتمتة، الأنواع، الاعتماديات، أمان النقل الاختياري، الـ migrations، المرونة، المراقبة، والتوفر**.

الثوابت المعمارية تبقى سارية (انظر `reconciliation-plan-vs-report.md` §3):
- `8728` يبقى المسار الافتراضي؛ لا يُفرض SSL كمسار أساسي.
- `librouteros` طبقة الاتصال الموحدة.
- `core/` تبقى خالية من Telegram.
- بوابات الجودة: `ruff` + `validate_handlers.py` + `py_compile` + `pytest`.

## المرحلة أ: أتمتة الجودة والاختبار

### أ-1: خط تكامل مستمر (CI)

الهدف: تحويل بوابات الجودة من تشغيل يدوي إلى pipeline آلي.

المناطق المتوقعة:
- تفعيل Git للمشروع (حالياً غير مستودع — شرط مسبق).
- `.github/workflows/ci.yml` (أو ما يوازيها حسب المضيف).
- `pyproject.toml` (إعدادات ruff/pytest).

معيار القبول:
- كل push/PR يشغّل:
  - `ruff check . --select F821`
  - `py -3.12 scripts/validate_handlers.py`
  - `py -3.12 -m pytest -q`
  - فحص الأنواع (انظر أ-2).
- فشل أي بوابة يمنع الدمج (branch protection).

ملاحظات توافق:
- يبقى التشغيل المحلي عبر `py -3.12` كما هو.
- لا يتطلب راوتراً حقيقياً (الاختبارات الوحدوية بـ mocks).

### أ-2: فحص الأنواع الثابت (mypy/pyright)

الهدف: اكتشاف أخطاء الأنواع دون تشغيل.

المناطق المتوقعة:
- `pyproject.toml` (قسم `[tool.mypy]`).
- `core/`, `bot/`, `utils/`, `database/`.

معيار القبول:
- `mypy .` يمرّ على `core/` (الأولوية القصوى لأنها بلا Telegram وقابلة للاختبار).
- تغطية تدريجية لبقية الوحدات عبر `strict` على الحزم الجديدة أولاً.
- يُضاف إلى CI (أ-1).

ملاحظات توافق:
- يُمنع تعطيل الفحص عبر `# type: ignore` إلا مع تعليل.
- لا يغيّر سلوك التشغيل.

### أ-3: تثبيت الاعتماديات (lockfile)

الهدف: تكرار البيئة بدقة عبر إصدارات مقفلة.

المناطق المتوقعة:
- `requirements.txt` + `requirements-dev.txt`.
- `requirements.lock` + `requirements-dev.lock` (عبر `pip-tools`).
- توثيق في `README.md`.

معيار القبول:
- `pip-compile` يولّد lock بم hashes.
- التشغيل الموثّق: `pip-sync requirements.lock requirements-dev.lock`.
- البناء في CI يستخدم الـ lock لا `pip install -r requirements.txt` العاري.

ملاحظات توافق:
- لا كسر لإصدارات `librouteros>=3.3`، `python-telegram-bot>=21`، `reportlab` الحالية.

### أ-4: اختبارات تكامل/عقود على v6 وv7

الهدف: تغطية فارق الحقول الفعلي بين الإصدارين (غير مغطى بـ mocks).

المناطق المتوقعة:
- `tests/integration/` (مشار إليها في أولوية 5 من الخطة الأصلية).
- `tests/contracts/` لمسارات `get_userman_base_path` وحقول restore.
- أداة تشغيل اختيارية ضد حاويات/راوترات v6 وv7 معزولة.

معيار القبول:
- مصفوفة: v6 مقابل v7 لكل أمر حساس (Hotspot users/active/hosts، User Manager users/profiles، restore fields، reset counters).
- فشل restore بسبب حقل غير مدعوم يُسجَّل ويُستكمل (يرتبط بأولوية 5 الأصلية).
- تُشغَّل في CI كـ job منفصل (يتطلب راوترات/حاويات متاحة أو تُعطّل افتراضياً).

ملاحظات توافق:
- لا تغيير في منطق `core/`؛ الاختبارات فقط.
- الحفاظ على `get_userman_base_path()` كمرجع مركزي.

## المرحلة ب: أمان النقل (اختياري، لا إجباري)

### ب-1: دعم API-SSL على المنفذ 8729 لـ v7

الهدف: السماح بنقل مشفّر حيث تتوفر شهادة على الراوتر، دون كسر v6.

المناطق المتوقعة:
- `config.py`: إضافة `API_USE_SSL` (افتراض `False`) و`DEFAULT_API_SECURE_PORT = 8729`.
- `core/connection_pool.py` / `core/mikrotik_api.py`: تمرير سياق TLS اختياري إلى `librouteros.connect(..., ssl=...)`.
- `utils/bot_commands.py` / `bot/messages.py`: خيار تبديل لكل راوتر.

معيار القبول:
- عند `API_USE_SSL=True` والراوتر v7 بشهادة، يُستخدم `8729` مع تحقق شهادة اختياري (self-signed tolerated عبر علم صريح).
- عند `False` يبقى `8728` كما هو (المسار الافتراضي).
- لا تأثير على v6 (يبقى 8728 غير مشفّر).
- `get_userman_base_path()` غير معني بالمنفذ.

ملاحظات توافق:
- هذا **دعم اختياري** لا فرض؛ يحترم قيد «الراوترات بلا شهادة» في البيئات الصغيرة.
- يوثَّق كخيار متقدم في `README.md`/`AGENTS.md`.

## المرحلة ج: قاعدة البيانات

### ج-1: إطار migrations رسمي ومُرقّم

الهدف: استبدال «migrations خفيفة» داخل `models.py` بإصدارة مُرقّمة idempotent.

المناطق المتوقعة:
- `database/migrations/` (ملفات `0001_init.sql`, `0002_roles.sql`, ...).
- `database/migrator.py` (يسجّل آخر إصدار مطبّق في جدول `schema_version`).
- `main.py`: استدعاء `migrator.upgrade()` بدل منطق الترقية الحالي.

معيار القبول:
- كل migration idempotent (يدعم إعادة التشغيل بأمان).
- ترتيب التطبيق مضمون ومرقّم.
- اختبار `tests/core/test_migrator.py` يطبّق/يعيد تطبيق الهجرات بنجاح.
- لا كسر للجداول الموجودة (discovered_routers, user_sessions, audit_log, ...).

ملاحظات توافق:
- يرتبط بأولوية 12 الأصلية (تقسيم DB)؛ يُنفَّذ معها.
- الحفاظ على SQLite WAL + `busy_timeout`.

## المرحلة د: المرونة والمراقبة

### د-1: Circuit Breaker لفشل API المتكرر

الهدف: حماية البوت والراوتر من حلقات إعادة المحاولة عند فشل مستمر.

المناطق المتوقعة:
- `core/resilience.py` (أو داخل `connection_pool.py`).
- `core/mikrotik_api.py`: تغليف الاستدعاءات الحرجة.

معيار القبول:
- بعد N إخفاق متتالٍ خلال نافذة زمنية، يُفتح الـ breaker ويرفض الطلبات مؤقتاً مع رسالة واضحة.
- بعد فترة cooldown، محاولة نصف مفتوحة (half-open) لاستكشاف التعافي.
- القيم (N، النافذة، cooldown) قابلة للضبط من config.
- لا تداخل مع retry/throttle الموجودة (الـ breaker فوقها).

ملاحظات توافق:
- لا اعتماد على Telegram داخل `core`.
- يقلّل الضجيج الذي يغذّي «التنبيهات الذكية» (أولوية 8 الموحّدة).

### د-2: مراقبة قابلة للآلة (metrics)

الهدف: تعريض مؤشرات للدغمة في نظام إنذار خارجي (بلا إعادة إنشاء HTTP server).

المناطق المتوقعة:
- `core/metrics.py` (موجود كهدف في أولوية 14 الأصلية).
- إما push إلى Prometheus Pushgateway، أو أمر/تصدير `/metrics` داخل البوت.
- لا إنشاء خادم HTTP مستقل (سبق إزالته عمداً).

معيار القبول:
- مؤشرات: عدد الاتصالات، معدل فشل API، مدة الـ retry، حالة كاش الإصدار، آخر فشل backup، آخر فشل watchdog.
- صيغة قابلة للاستهلاك الآلي (text exposition format).
- لا تسريب أسرار/كلمات مرور في المخرجات.

ملاحظات توافق:
- يبقى `request_id` في السجلات كما هو.
- `core` يُنتج القيم؛ العرض في `utils`/`bot`.

## بوابات الجودة المضافة

بعد كل تغيير في هذه الخطة:

```bash
ruff check . --select F821 --exclude venv --exclude __pycache__ --exclude backups --exclude logs --exclude _releases
py -3.12 scripts/validate_handlers.py
mypy core/            # بعد أ-2
py -3.12 -m pytest -q
```

عند تعديل handlers/commands: تحديث `utils/registrations.py` + `utils/bot_commands.py` + `bot/messages.py` + تشغيل `validate_handlers.py`.

## ترتيب التنفيذ المقترح (ما بعد الخطة)

1. تفعيل Git + أ-1 (CI) + أ-2 (mypy على core) + أ-3 (lockfile) — أساس الأتمتة.
2. أ-4 (اختبارات تكامل v6/v7) — يرفع ثقة التوافق.
3. ج-1 (migrations رسمية) — يسبق أي توسع DB كبير.
4. د-1 (circuit breaker) + د-2 (metrics) — يحسّن المرونة والمراقبة.
5. ب-1 (API-SSL اختياري على v7) — يعزّز الأمان حيث تتوفر شهادة.
6. هـ-1 يُوثَّق فقط ولا يُنفَّذ ككود.

## القرارات المفتوحة

1. مضيف CI: GitHub Actions أم GitLab CI أم غيره (يعتمد على مكان استضافة المستودع بعد تفعيل Git)؟
2. أداة types: `mypy` أم `pyright`؟ **توصيتي: mypy** لبساطة الدمج مع المشروع الحالي.
3. أداة lockfile: `pip-tools` أم `poetry`؟ **توصيتي: pip-tools** لأن المشروع يعتمد بالفعل `requirements.txt`/`requirements-dev.txt` العاديين.
4. أداة migrations: `SQLite3` خام مُرقّم (خفيف، بلا اعتماد) أم `alembic`؟ **توصيتي: خام مُرقّم** لتجنّب اعتماد ثقيل وملاءمة SQLite الحالي.
5. Pushgateway مقابل أمر `/metrics` داخلي؟ **توصيتي: /metrics** لتجنّب بنية خارجية إضافية.
